# trajectory-eval

Automatically derive behavior contracts from LLM agent execution traces.

Given a recorded agent trajectory (a sequence of user messages, LLM responses, tool calls, and tool results), `trajectory-eval` generates two structured artifacts:

- **BehaviorContract** — deterministic, step-agnostic invariants that describe what the agent *must* do (data dependencies, tool sequences, parameter types, output formats, grounding claims, etc.)
- **ExecutionReport** — behavioral observations and performance metrics (token budget, latency, tool output utilization, redundancy rate, etc.)

## How it works

Rules are generated by a set of `HardRule` subclasses that each analyze one aspect of the trajectory:

| Rule | What it checks |
|---|---|
| `DataDependencyRule` | Value- and type-based data flow between tool outputs and subsequent inputs |
| `ToolSequenceRule` | Which tool pairs appear in sequence and with what confidence |
| `ToolResultTypeRule` | Detected content type of each tool output (JSON, XML, Python, file path, …) |
| `LlmGroundingRule` | Whether entity references in LLM responses can be traced to prior tool results |
| `LlmResponseFormatRule` | Format compliance of LLM responses |
| `TerminalStateRule` | Whether the trajectory reaches a valid terminal state |
| `MutationMatcherRule` | Whether the agent adapts after a failed or empty tool result |
| `TokenBudgetRule` | Per-step token count stays within budget |
| `LatencyBudgetRule` | Per-step latency stays within budget |
| `ToolOutputUtilizationRule` | Whether tool outputs are consumed by later steps |
| `LlmResponseUtilizationRule` | Whether LLM response content is consumed by later steps |
| `RedundancyRateRule` | Fraction of duplicate tool calls stays below threshold |

Rules are passed through an emitter (producing `CompiledRule` instances), a deduplicator (merging identical rules, flagging conflicts), and assembled into the final contract and report by `ContractCompiler`.

## Installation

Requires Python 3.10+.

```bash
pip install -e ".[dev]"
```

Copy `.env.example` to `.env` and fill in your Azure AI Foundry credentials (only needed for LLM-assisted rules like `LlmGroundingRule`):

```
AZURE_FOUNDRY_ENDPOINT=https://<resource>.services.ai.azure.com/models
AZURE_FOUNDRY_KEY=<your-key>
AZURE_FOUNDRY_MODEL=DeepSeek-V4-0
```

## Usage

```bash
python eval_traj.py examples/1.json
```

Output is a JSON object on stdout:

```json
{
  "contract": { "schema_version": 2, "rules": [ ... ] },
  "report":   { "metrics": [ ... ], "flags": [ ... ] }
}
```

The trajectory format is auto-detected: Langfuse observation exports (arrays containing `"type": "GENERATION"` entries) and SWE-bench message-list files are both supported.

## Running tests

```bash
pytest
```

## Project layout

```
trajectory_eval/
  models/           # Pydantic models: Trajectory, Step, Tool, BehaviorContract, …
  generator/
    rules/          # One HardRule subclass per behavioral aspect
    emitter.py      # HardRule → CompiledRule conversion
    deduplicator.py # Merge identical rules, detect conflicts
    contract_compiler.py  # Orchestrates the full pipeline
    report_builder.py
  parsers/          # Trajectory file parsers (SWE-bench, Langfuse)
    parameter/      # Tool input parameter type detection
  llm/              # LLM client (Azure AI Foundry)
eval_traj.py        # CLI entry point
examples/           # Sample trajectory files
```
